# Cart API — документація кошика

Документ описує фактичні маршрути `CartController` та поведінку відповідних методів `DataAccessor`: отримання кошика, додавання товарів, зміну кількості, видалення позицій і очищення кошика.

## Перед початком

У прикладах `{{baseUrl}}` — базова адреса запущеного API, наприклад `https://localhost:7001`.

Усі маршрути кошика доступні лише авторизованому користувачу з роллю `User`. Для кожного запиту передавайте JWT access token:

```http
Authorization: Bearer {{userToken}}
```

Кошик визначається за ID користувача з JWT (`sub` або `NameIdentifier`). Передавати `userId` у URL чи тілі запиту не потрібно. `Manager` та `Admin` не мають доступу до цих маршрутів: контролер має `[Authorize(Roles = AppRoles.User)]`.

Поточна культура HTTP-запиту використовується для назви товару та локалізованого відображення статусу доступності. У застосунку підтримуються `uk-UA` та `en-US`; якщо перекладу товару для поточної культури немає, використовується `uk-UA`, а якщо немає і його — SKU товару.

## Короткий список endpoint-ів

| Метод | URL | Доступ | Призначення |
|---|---|---|---|
| `GET` | `/api/cart` | `User` | Отримати поточний кошик |
| `POST` | `/api/cart/items` | `User` | Додати товар або збільшити кількість наявної позиції |
| `PUT` | `/api/cart/items/{productId}` | `User` | Встановити нову кількість товару |
| `DELETE` | `/api/cart/items/{productId}` | `User` | Видалити товар із кошика |
| `DELETE` | `/api/cart` | `User` | Очистити кошик |

## Формат відповіді

Успішні відповіді та контрольовані помилки контролера використовують `RestResponse`:

```json
{
  "status": {
    "isOk": true,
    "code": 200,
    "message": "OK"
  },
  "meta": {
    "apiName": "Cart",
    "dataType": "application/json",
    "cacheTime": 0,
    "manipulations": ["GET"],
    "links": {
      "self": "/api/cart"
    }
  },
  "data": {
    "items": [],
    "totalAvailableQuantity": 0,
    "totalAmount": 0
  }
}
```

Для помилок автоматичної перевірки DataAnnotations через `[ApiController]` ASP.NET Core може повернути стандартний `ValidationProblemDetails`, а не `RestResponse`. Зокрема, це стосується значення `quantity`, яке не проходить `[Range]`.

## 1. Отримати кошик

```http
GET {{baseUrl}}/api/cart
Authorization: Bearer {{userToken}}
```

Успіх — `200 OK`. Якщо запис кошика ще не створений або в ньому немає позицій, API повертає порожній `CartResponseDto`. Сам GET-запит не створює кошик.

Приклад `data` для кошика з однією позицією:

```json
{
  "items": [
    {
      "id": "00000000-0000-0000-0000-000000000010",
      "productId": "00000000-0000-0000-0000-000000000001",
      "sku": "PHONE-001",
      "productName": "Приклад смартфона",
      "originalUnitPrice": 10000.00,
      "unitPrice": 9000.00,
      "activePromotion": {
        "promotionId": "00000000-0000-0000-0000-000000000100",
        "title": "Знижка на смартфон",
        "slug": "znizhka-na-smartfon",
        "discountType": "Percentage",
        "discountValue": 10.00,
        "originalPrice": 10000.00,
        "discountAmount": 1000.00,
        "discountedPrice": 9000.00
      },
      "requestedQuantity": 5,
      "availableQuantity": 3,
      "stockQuantity": 3,
      "isProductActive": true,
      "isAvailable": true,
      "isQuantityAdjusted": true,
      "availabilityStatus": "InsufficientStock",
      "availabilityStatusDisplayName": "Недостатня кількість на складі",
      "lineTotal": 27000.00
    }
  ],
  "totalAvailableQuantity": 3,
  "totalAmount": 27000.00
}
```

Усі значення в прикладі ілюстративні. `activePromotion` має значення `null`, якщо для товару не застосовується активна акція.

### Поля позиції кошика

| Поле | Значення |
|---|---|
| `id` | ID запису `CartItem` |
| `productId` | ID товару |
| `sku` | Поточний SKU товару |
| `productName` | Назва товару поточною мовою, fallback — `uk-UA`, потім SKU |
| `originalUnitPrice` | Поточна базова ціна товару з БД |
| `unitPrice` | Поточна ціна одиниці з урахуванням застосованої акції, якщо вона є |
| `activePromotion` | Інформація про застосовану акцію або `null` |
| `requestedQuantity` | Кількість, яку користувач зберіг у кошику |
| `availableQuantity` | Кількість, доступна зараз для придбання |
| `stockQuantity` | Поточний залишок товару; у відповіді не відображається від'ємне значення |
| `isProductActive` | Чи активний товар |
| `isAvailable` | `true`, якщо доступна хоча б одна одиниця (`availableQuantity > 0`) |
| `isQuantityAdjusted` | `true`, якщо доступна кількість відрізняється від запитаної |
| `availabilityStatus` | Машинне значення статусу доступності |
| `availabilityStatusDisplayName` | Локалізована назва статусу для інтерфейсу |
| `lineTotal` | `unitPrice × availableQuantity`, округлено до двох знаків після коми |

### Кількість і доступність

Збережене `CartItem.Quantity` є запитаною кількістю. Під час читання кошика backend не переписує її через зміну складського залишку, а обчислює окрему доступну кількість:

- для активного товару `availableQuantity` дорівнює меншому з `requestedQuantity` і поточного невід'ємного залишку;
- для неактивного товару `availableQuantity` дорівнює `0`;
- `stockQuantity` у відповіді обчислюється як `Math.Max(Product.StockQuantity, 0)`.

Можливі значення `availabilityStatus`:

| Значення | Умова |
|---|---|
| `Inactive` | Товар деактивований; цей стан має пріоритет над іншими |
| `OutOfStock` | Товар активний, але залишок дорівнює нулю |
| `InsufficientStock` | Товар активний, залишок є, але він менший за запитану кількість |
| `Available` | Товар активний і вся запитана кількість доступна |

**Важливо:** `isAvailable` не означає, що доступна вся запитана кількість. Наприклад, коли користувач запросив 5 одиниць, а на складі залишилося 3, `isAvailable` буде `true`, `availableQuantity` — `3`, `isQuantityAdjusted` — `true`, а `availabilityStatus` — `InsufficientStock`.

`totalAvailableQuantity` — сума `availableQuantity` усіх позицій. `totalAmount` — сума `lineTotal` усіх позицій. Для неактивного товару або товару без залишку `availableQuantity` і `lineTotal` дорівнюють нулю.

Ціни в кошику не зберігаються в `CartItem`: під час кожного читання використовуються поточна ціна товару та доступні на цей момент акції. Отже, ціна й сума кошика можуть змінитися між запитами. Остаточна ціна фіксується вже в замовленні під час оформлення.

## 2. Додати товар

```http
POST {{baseUrl}}/api/cart/items
Authorization: Bearer {{userToken}}
Content-Type: application/json
```

Тіло запиту:

```json
{
  "productId": "00000000-0000-0000-0000-000000000001",
  "quantity": 2
}
```

`productId` — GUID товару. `quantity` — ціле число від 1. Якщо поле `quantity` не передане, DTO використовує значення `1` за замовчуванням. Порожній `productId` (`Guid.Empty`, зокрема коли його не передано) відхиляється контролером із `400 Bad Request`.

Перед додаванням backend перевіряє, що товар існує, активний і має достатній залишок. Якщо товар уже є в кошику, передана кількість додається до наявної. Загальна запитана кількість після додавання також не може перевищувати поточний залишок.

Успіх — `200 OK` з оновленим `CartResponseDto`. `201 Created` не використовується.

Типові помилки:

| Код | Причина |
|---|---|
| `400 Bad Request` | Порожній `productId`, `quantity < 1` або помилка валідації запиту |
| `401 Unauthorized` | Відсутній, недійсний або прострочений JWT |
| `403 Forbidden` | Користувач не має ролі `User` |
| `404 Not Found` | Товар із таким ID не існує |
| `409 Conflict` | Товар неактивний, його немає на складі або загальна кількість у кошику перевищить залишок |

Якщо товар уже присутній у кошику, backend спочатку перевіряє товар, потім блокує рядок кошика й повторно читає товар із блокуванням, щоб перевірити актуальний залишок перед зміною позиції.

## 3. Змінити кількість товару

```http
PUT {{baseUrl}}/api/cart/items/{{productId}}
Authorization: Bearer {{userToken}}
Content-Type: application/json
```

Тіло запиту:

```json
{
  "quantity": 3
}
```

`quantity` — ціле число від 1. Це нова запитана кількість, а не приріст до попереднього значення. Backend перевіряє існування позиції, активність товару та достатність поточного залишку. Значення, більше за поточний залишок, не приймається.

Успіх — `200 OK` з оновленим `CartResponseDto`.

- `400 Bad Request` — порожній `productId` або кількість не проходить валідацію;
- `401 Unauthorized` / `403 Forbidden` — проблема з JWT або роллю;
- `404 Not Found` — кошик або позиція з таким `productId` не знайдені;
- `409 Conflict` — товар неактивний, відсутній на складі або нова кількість перевищує залишок.

## 4. Видалити товар із кошика

```http
DELETE {{baseUrl}}/api/cart/items/{{productId}}
Authorization: Bearer {{userToken}}
```

Успіх — `200 OK` з оновленим `CartResponseDto`. Якщо кошик або позицію не знайдено, повертається `404 Not Found`. Порожній `productId` повертає `400 Bad Request`.

Видалення позиції не вимагає, щоб товар залишався активним або був у наявності: endpoint видаляє саме запис кошика.

## 5. Очистити кошик

```http
DELETE {{baseUrl}}/api/cart
Authorization: Bearer {{userToken}}
```

Успіх — `200 OK` з порожнім `CartResponseDto`:

```json
{
  "items": [],
  "totalAvailableQuantity": 0,
  "totalAmount": 0
}
```

Якщо запису кошика ще немає, endpoint також повертає `200 OK` із порожнім результатом. Існуючий запис кошика залишається в БД, видаляються його позиції.

## 6. Правила та поведінка

- Для одного користувача може існувати лише один кошик: це забезпечено унікальним індексом `Carts.UserId`.
- Кошик створюється під час першого успішного додавання товару; простий `GET` його не створює.
- Один товар може мати лише одну позицію в кошику: у БД є унікальний індекс `(CartId, ProductId)`.
- Кількість позиції має бути більшою за нуль: у БД є check constraint `Quantity > 0`.
- Зменшення складського залишку не змінює збережену запитану кількість у кошику; доступність перераховується під час читання.
- Додавання та явна зміна кількості перевіряють активність товару й актуальний залишок.
- Неактивні товари можуть залишатися в раніше створеному кошику, але повертаються з `availableQuantity = 0` і статусом `Inactive`; оформити таке замовлення не можна.
- Ціни та знижки розраховуються сервером. Клієнт не передає ціну, суму чи знижку.
- Зміни кошика використовують транзакції та блокування рядка кошика. Під час додавання й зміни кількості товар також повторно читається з блокуванням, оскільки ці операції залежать від залишку. Видалення позиції та очищення кошика не потребують блокування товарів.
- Під час додавання нового товару запис кошика за потреби створюється до транзакції зміни позицій; конкурентне створення кошика для одного користувача обробляється через унікальний індекс і повторне читання запису.

## 7. Перевірка через Postman

1. Увійдіть під користувачем із роллю `User` та скопіюйте `data.accessToken`.
2. Виконайте `GET /api/cart` для нового користувача — очікується порожній кошик.
3. Додайте активний товар через `POST /api/cart/items`.
4. Повторіть POST для того самого товару й перевірте, що кількість збільшилась в одній позиції.
5. Перевірте `GET /api/cart` та поля `requestedQuantity`, `availableQuantity`, `isAvailable` і `availabilityStatus`.
6. Змініть кількість через `PUT /api/cart/items/{productId}`.
7. Перевірте видалення позиції через `DELETE /api/cart/items/{productId}` та очищення через `DELETE /api/cart`.
8. Перевірте неіснуючий, неактивний товар і недостатній залишок.
9. Викличте endpoint кошика без токена та з ролями `Manager` і `Admin`: очікується відмова в доступі (`401` або `403` відповідно до стану автентифікації).
