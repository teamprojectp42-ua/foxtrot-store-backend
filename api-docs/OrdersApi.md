# Orders API — документація замовлень

Документ описує фактичні маршрути `OrdersController` і відповідну поведінку `DataAccessor`: оформлення замовлення з кошика, перегляд власних та всіх замовлень, отримання деталей і зміну статусу.

## Перед початком

У прикладах `{{baseUrl}}` — базова адреса запущеного API, наприклад `https://localhost:7001`.

Для захищених запитів передавайте JWT access token:

```http
Authorization: Bearer {{accessToken}}
```

Розподіл доступу:

| Роль | Дозволені операції |
|---|---|
| `User` | Оформлення замовлення з власного кошика та перегляд власних замовлень |
| `Manager` | Перегляд усіх замовлень, деталей і зміна статусів |
| `Admin` | Ті самі операції із замовленнями, що й `Manager` |

ID покупця для користувацьких операцій береться з JWT (`sub` або `NameIdentifier`). Клієнт не передає `UserId`.

Назва товару, яка зберігається у знімку позиції замовлення, визначається поточною культурою запиту з fallback на `uk-UA`, а потім на SKU. `StatusDisplayName` також локалізується відповідно до поточної культури.

## Короткий список endpoint-ів

| Метод | URL | Доступ | Призначення |
|---|---|---|---|
| `POST` | `/api/orders` | `User` | Оформити замовлення з поточного кошика |
| `GET` | `/api/orders/my` | `User` | Отримати власні замовлення |
| `GET` | `/api/orders/admin` | `Manager`, `Admin` | Отримати всі замовлення |
| `GET` | `/api/orders/admin/{id}` | `Manager`, `Admin` | Отримати деталі замовлення |
| `PUT` | `/api/orders/admin/{id}/status` | `Manager`, `Admin` | Змінити статус замовлення |

Поточна реалізація не має endpoint-а для видалення замовлення, редагування адреси після оформлення або окремого отримання замовлення користувачем за ID.

## Формат відповіді

Успішні відповіді та контрольовані помилки використовують `RestResponse`:

```json
{
  "status": {
    "isOk": true,
    "code": 200,
    "message": "OK"
  },
  "meta": {
    "apiName": "Orders",
    "dataType": "application/json",
    "cacheTime": 0,
    "manipulations": ["GET"],
    "links": {
      "self": "/api/orders/my"
    }
  },
  "data": []
}
```

Помилки автоматичної перевірки DataAnnotations через `[ApiController]` можуть повертатися у форматі `ProblemDetails`, а не `RestResponse`. Помилки, які контролер обробляє самостійно, повертаються в `RestResponse`.

## Статуси та переходи

Backend використовує значення `OrderStatus`:

| Значення API | Відображення |
|---|---|
| `New` | Нове замовлення |
| `Processing` | В обробці |
| `Completed` | Виконане |
| `Cancelled` | Скасоване |

`status` у JSON містить машинне значення enum (`New`, `Processing`, `Completed`, `Cancelled`), а `statusDisplayName` — локалізований текст для інтерфейсу.

Дозволені переходи:

| Поточний статус | Новий статус | Результат |
|---|---|---|
| `New` | `Processing` | Дозволено |
| `New` | `Cancelled` | Дозволено; товар повертається на склад |
| `Processing` | `Completed` | Дозволено |
| `Processing` | `Cancelled` | Дозволено; товар повертається на склад |
| `Completed` | інший статус | Заборонено |
| `Cancelled` | інший статус | Заборонено |

Повторне надсилання поточного статусу приймається як операція без змін: повертається `200 OK`, дата оновлення та побічні операції не повторюються. Тому повторне встановлення `Cancelled` не повертає товар на склад вдруге.

## 1. Оформити замовлення

Замовлення створюється з кошика поточного авторизованого користувача. Клієнт передає лише контактні й адресні дані.

```http
POST {{baseUrl}}/api/orders
Authorization: Bearer {{userToken}}
Content-Type: application/json
```

Тіло запиту:

```json
{
  "fullName": "Іван Іванов",
  "phoneNumber": "+380991234567",
  "city": "Одеса",
  "deliveryAddress": "Нова пошта, відділення 10",
  "comment": "Зателефонувати перед доставкою"
}
```

### Поля запиту

| Поле | Правила |
|---|---|
| `fullName` | Обов'язкове, від 2 до 200 символів |
| `phoneNumber` | Обов'язкове, `[Phone]`, від 7 до 30 символів |
| `city` | Обов'язкове, від 2 до 150 символів |
| `deliveryAddress` | Обов'язкове, від 3 до 500 символів |
| `comment` | Необов'язкове, максимум 1000 символів |

Значення зберігаються після обрізання пробілів по краях. Порожній або відсутній коментар зберігається як `null`.

### Що клієнт не повинен передавати

Не додавайте до запиту `userId`, список товарів, `productId`, кількість, ціни, знижки або `totalAmount`. Backend бере покупця з JWT, склад замовлення — з кошика, а актуальні ціни та застосовні акції — з бази даних.

### Перевірки та оформлення

Під час оформлення backend виконує операції в одній транзакції:

1. Блокує рядок кошика користувача, щоб інші запити не змінювали його одночасно з оформленням.
2. Перевіряє, що кошик існує та містить позиції.
3. Отримує товари з кошика та блокує рядки товарів у стабільному порядку за ID.
4. Повторно перевіряє існування, активність і залишок кожного товару.
5. Отримує актуальні застосовні акції та розраховує ціну одиниці.
6. Створює замовлення зі статусом `New`.
7. Створює позиції замовлення зі знімками назви, SKU, ціни, кількості та суми.
8. Зменшує складський залишок кожного придбаного товару.
9. Видаляє позиції з кошика.
10. Зберігає замовлення, позиції, зміни залишків і очищення кошика та фіксує транзакцію.

Якщо операція до фіксації транзакції завершується помилкою, зміни замовлення, залишків і позицій кошика відкочуються.

### Нестача товару

Кошик може показувати `availableQuantity`, меншу за `requestedQuantity`, але під час оформлення backend вимагає всю запитану кількість. Наприклад, якщо в кошику запитано 5 одиниць, а на складі залишилося 3, замовлення не буде автоматично оформлено на 3 одиниці. API поверне `409 Conflict`; покупець має змінити кількість у кошику й повторити оформлення.

Якщо товар став неактивним після додавання в кошик, оформлення також відхиляється. Якщо товар, на який посилається позиція кошика, більше не знайдений, поточна реалізація теж повертає `409 Conflict`.

### Успішна відповідь

Успішне створення повертає HTTP `201 Created`; об'єкт `OrderDto` міститься в `data` оболонки `RestResponse`:

```json
{
  "status": {
    "isOk": true,
    "code": 201,
    "message": "Created"
  },
  "meta": {
    "apiName": "Orders",
    "dataType": "application/json",
    "cacheTime": 0,
    "manipulations": ["POST"],
    "links": {
      "self": "/api/orders/my"
    }
  },
  "data": {
    "id": "00000000-0000-0000-0000-000000000200",
    "customerName": "Іван Іванов",
    "phoneNumber": "+380991234567",
    "city": "Одеса",
    "deliveryAddress": "Нова пошта, відділення 10",
    "comment": "Зателефонувати перед доставкою",
    "totalAmount": 18000.00,
    "status": "New",
    "statusDisplayName": "Нове",
    "createdAt": "2026-11-10T10:00:00Z",
    "updatedAt": "2026-11-10T10:00:00Z",
    "items": [
      {
        "id": "00000000-0000-0000-0000-000000000201",
        "productId": "00000000-0000-0000-0000-000000000001",
        "productName": "Приклад смартфона",
        "productSku": "PHONE-001",
        "unitPrice": 9000.00,
        "quantity": 2,
        "totalPrice": 18000.00
      }
    ]
  }
}
```

Значення в прикладі ілюстративні. Відповідне поле `customerName` формується з `fullName` запиту. Дати створення й оновлення встановлюються сервером у UTC.

Типові помилки:

| Код | Причина |
|---|---|
| `400 Bad Request` | Некоректні контактні/адресні поля або помилка аргументів |
| `401 Unauthorized` | Відсутній, недійсний або прострочений JWT |
| `403 Forbidden` | Користувач не має ролі `User` |
| `409 Conflict` | Кошик відсутній або порожній; товар неактивний; недостатній залишок; товар із кошика не знайдений |

Для невдалих перевірок DataAnnotations можливий `ProblemDetails`; помилки бізнес-логіки, перехоплені контролером, повертаються в `RestResponse`.

## 2. Отримати власні замовлення

```http
GET {{baseUrl}}/api/orders/my
Authorization: Bearer {{userToken}}
```

Доступно лише ролі `User`. Backend бере `UserId` із JWT і повертає тільки замовлення цього користувача. Передати ID іншого користувача в запиті неможливо.

Успіх — `200 OK`; `data` містить масив `OrderDto`. Список відсортований за `CreatedAt` за спаданням, а за однакового часу — за `Id` за спаданням. Пагінації немає. Якщо замовлень немає, повертається порожній масив.

## 3. Отримати всі замовлення

```http
GET {{baseUrl}}/api/orders/admin
Authorization: Bearer {{managerToken}}
```

Доступно ролям `Manager` та `Admin`. Успіх — `200 OK`; `data` містить усі замовлення з позиціями, відсортовані за `CreatedAt` за спаданням, а потім за `Id` за спаданням. Пагінації немає.

## 4. Отримати деталі замовлення

```http
GET {{baseUrl}}/api/orders/admin/{{orderId}}
Authorization: Bearer {{managerToken}}
```

Доступно ролям `Manager` та `Admin`. `orderId` має бути GUID. Порожній GUID повертає `400 Bad Request`; якщо замовлення не знайдено — `404 Not Found`. Успіх — `200 OK` з одним `OrderDto` у `data`.

Деталі містять контактні дані отримувача, адресу доставки, коментар, загальну суму, статус і позиції замовлення. Окремого endpoint-а для отримання одного замовлення покупцем немає: покупець отримує список власних замовлень через `/api/orders/my`.

## 5. Змінити статус замовлення

```http
PUT {{baseUrl}}/api/orders/admin/{{orderId}}/status
Authorization: Bearer {{managerToken}}
Content-Type: application/json
```

Тіло запиту:

```json
{
  "status": "Processing"
}
```

Дозволені значення: `New`, `Processing`, `Completed`, `Cancelled`. Перевірка назв не враховує регістр, але числові значення enum не приймаються. Поле `status` обов'язкове й має довжину до 20 символів.

Успіх — `200 OK` з оновленим `OrderDto` у `data`. Повторне передавання вже встановленого статусу також повертає `200 OK`, але не змінює `UpdatedAt` і не запускає повторно побічні операції.

Під час переходу в `Cancelled` backend у межах транзакції:

1. Блокує рядок замовлення.
2. Перевіряє допустимість переходу.
3. Отримує позиції замовлення та блокує пов'язані товари в стабільному порядку за ID.
4. Повертає зарезервовану кількість кожного товару в `StockQuantity`.
5. Змінює статус і `UpdatedAt`.
6. Зберігає зміни та фіксує транзакцію.

Якщо повернення залишку неможливе (наприклад, результат перевищив би максимальне значення `Int32`), операція завершується `409 Conflict`, а транзакція не фіксується. Фізичне видалення товару, на який посилається позиція замовлення, обмежене зовнішнім ключем `DeleteBehavior.Restrict`.

Типові помилки:

| Код | Причина |
|---|---|
| `400 Bad Request` | Порожній ID, відсутній або невідомий статус, числовий запис enum |
| `401 Unauthorized` | Відсутній, недійсний або прострочений JWT |
| `403 Forbidden` | Користувач не має ролі `Manager` або `Admin` |
| `404 Not Found` | Замовлення не знайдено |
| `409 Conflict` | Недопустимий перехід статусу, відсутній товар під час повернення залишку або неможливість повернути кількість через переповнення |

## 6. Структура OrderDto та OrderItemDto

```json
{
  "id": "00000000-0000-0000-0000-000000000200",
  "customerName": "Іван Іванов",
  "phoneNumber": "+380991234567",
  "city": "Одеса",
  "deliveryAddress": "Нова пошта, відділення 10",
  "comment": null,
  "totalAmount": 18000.00,
  "status": "New",
  "statusDisplayName": "Нове",
  "createdAt": "2026-11-10T10:00:00Z",
  "updatedAt": "2026-11-10T10:00:00Z",
  "items": [
    {
      "id": "00000000-0000-0000-0000-000000000201",
      "productId": "00000000-0000-0000-0000-000000000001",
      "productName": "Приклад смартфона",
      "productSku": "PHONE-001",
      "unitPrice": 9000.00,
      "quantity": 2,
      "totalPrice": 18000.00
    }
  ]
}
```

| Поле | Значення |
|---|---|
| `id` | ID замовлення |
| `customerName` | Ім'я отримувача, отримане з `fullName` під час оформлення |
| `phoneNumber`, `city`, `deliveryAddress` | Контактні та адресні дані замовлення |
| `comment` | Коментар або `null` |
| `totalAmount` | Загальна сума зафіксованих позицій замовлення |
| `status` | Машинне значення `OrderStatus` |
| `statusDisplayName` | Локалізоване відображення статусу |
| `createdAt`, `updatedAt` | Час створення та останньої зміни в UTC |
| `items` | Позиції замовлення |

У `OrderItemDto`:

- `productName` і `productSku` — знімки назви та SKU на момент оформлення;
- `unitPrice` — ціна одиниці на момент оформлення з урахуванням застосованої знижки;
- `quantity` — придбана кількість;
- `totalPrice` — сума позиції, розрахована сервером;
- `productId` — посилання на товар, з якого створено позицію.

Подальша зміна назви, SKU або ціни товару не змінює збережені знімки в історії замовлення. `OrderItem` не зберігає окреме поле з назвою акції; у ньому фіксується кінцева ціна одиниці.

## 7. Залишки, транзакції та історія

- Під час оформлення замовлення `Product.StockQuantity` зменшується на всю придбану кількість у тій самій транзакції, у якій створюються замовлення й позиції та очищується кошик.
- Кошик очищується лише в межах успішного оформлення. Якщо транзакція не фіксується, видалення позицій кошика також відкочується.
- Під час скасування замовлення зі статусу `New` або `Processing` зарезервована кількість повертається на склад.
- Повторне встановлення `Cancelled` не повертає залишок повторно.
- `Completed` і `Cancelled` — кінцеві статуси; переходи з них в інші статуси заборонені.
- Позиція кошика не зберігає ціну; замовлення зберігає ціну, назву та SKU на момент покупки.
- Зв'язок `OrderItem.Product` має `DeleteBehavior.Restrict`, тому товар із позиціями в історії замовлень не можна фізично видалити через БД. Для приховування товару використовується деактивація.
- Зв'язок `Order.User` також має `DeleteBehavior.Restrict`: наявність замовлень перешкоджає фізичному видаленню Identity-користувача.
- Онлайн-оплата, інтеграція з перевізником і створення накладних цими endpoint-ами не реалізовані.

## 8. Перевірка через Postman

1. Увійдіть під користувачем `User` та отримайте JWT.
2. Додайте активний товар у кошик через `POST /api/cart/items`.
3. Перевірте `GET /api/cart`, зокрема запитану й доступну кількість.
4. Оформіть замовлення через `POST /api/orders`.
5. Переконайтеся, що відповідь має HTTP `201`, кошик очищено, а складський залишок зменшився.
6. Виконайте `GET /api/orders/my` і перевірте наявність замовлення.
7. Увійдіть під `Manager` або `Admin` і перевірте `GET /api/orders/admin` та `GET /api/orders/admin/{id}`.
8. Переведіть замовлення `New` → `Processing` → `Completed` і перевірте, що наступний перехід заборонений.
9. Створіть інше замовлення та перевірте скасування `New` → `Cancelled` або `Processing` → `Cancelled`; залишок має відновитися один раз.
10. Перевірте, що `User` не має доступу до адміністративних маршрутів, а `Manager` не має доступу до маршрутів кошика й адміністративних операцій каталогу та користувачів.
