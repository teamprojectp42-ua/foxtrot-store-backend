# Orders API — інструкція з використання

Цей документ описує оформлення замовлення, перегляд власних замовлень, адміністративний перегляд усіх замовлень та зміну їхніх статусів у Foxtrot Store Backend.

## Перед початком

У прикладах `{{baseUrl}}` — базова адреса запущеного API, наприклад `https://localhost:7001`. Використовуйте адресу, яку показує застосунок під час запуску.

Для захищених запитів передавайте JWT access token:

```http
Authorization: Bearer {{accessToken}}
```

Розподіл доступу:

- `User` — оформлення замовлення та перегляд власних замовлень;
- `Manager` — перегляд усіх замовлень, деталей замовлення та зміна статусу;
- `Admin` — ті самі операції із замовленнями, що й `Manager`.

ID покупця для користувацьких операцій береться з JWT. Клієнт не передає `UserId`.

## Короткий список endpoint-ів

| Метод | URL | Призначення | Доступ |
|---|---|---|---|
| `POST` | `/api/orders` | Оформити замовлення з поточного кошика | `User` |
| `GET` | `/api/orders/my` | Отримати власні замовлення | `User` |
| `GET` | `/api/orders/admin` | Отримати всі замовлення | `Manager`, `Admin` |
| `GET` | `/api/orders/admin/{id}` | Отримати деталі замовлення | `Manager`, `Admin` |
| `PUT` | `/api/orders/admin/{id}/status` | Змінити статус замовлення | `Manager`, `Admin` |

## Статуси замовлення

Backend використовує такі значення `OrderStatus`:

| Значення API | Значення |
|---|---|
| `New` | Нове замовлення |
| `Processing` | Обробляється |
| `Completed` | Виконане |
| `Cancelled` | Скасоване |

Дозволені переходи:

| Поточний статус | Новий статус | Дозволено |
|---|---|---|
| `New` | `Processing` | Так |
| `New` | `Cancelled` | Так |
| `Processing` | `Completed` | Так |
| `Processing` | `Cancelled` | Так |
| `Completed` | будь-який інший | Ні |
| `Cancelled` | будь-який інший | Ні |

Повторне надсилання вже встановленого статусу не змінює замовлення повторно та не повторює побічні операції з залишками.

## 1. Оформити замовлення

Замовлення створюється з кошика поточного авторизованого користувача. Клієнт передає лише контактні та адресні дані.

```http
POST {{baseUrl}}/api/orders
Authorization: Bearer {{userToken}}
Content-Type: application/json
```

Тіло запиту:

```json
{
  "fullName": "Іван Іванов",
  "phoneNumber": "+380991234567",
  "city": "Одеса",
  "deliveryAddress": "Нова пошта, відділення 10",
  "comment": "Зателефонувати перед доставкою"
}
```

### Поля запиту

| Поле | Правила |
|---|---|
| `fullName` | Обов'язкове, від 2 до 200 символів |
| `phoneNumber` | Обов'язкове, від 7 до 30 символів, має відповідати `[Phone]` validation |
| `city` | Обов'язкове, від 2 до 150 символів |
| `deliveryAddress` | Обов'язкове, від 3 до 500 символів |
| `comment` | Необов'язкове, максимум 1000 символів |

### Що клієнт не повинен передавати

Не додавайте до запиту `userId`, товари, `productId`, кількість, ціни, знижки або `totalAmount`. Backend бере покупця з JWT, склад замовлення — з кошика, а актуальні ціни та акції — з бази даних.

### Перевірки та обробка на backend

Під час оформлення backend:

1. Блокує кошик користувача та отримує його позиції.
2. Відхиляє порожній кошик.
3. Блокує товари в стабільному порядку за ID.
4. Перевіряє, що кожен товар існує, активний і має достатній залишок для всієї запитаної кількості.
5. Отримує актуальні чинні акції та визначає найвигіднішу ціну для кожного товару.
6. Створює замовлення зі статусом `New`.
7. Зберігає в кожній позиції знімок назви, SKU, остаточної ціни, кількості та суми позиції.
8. Зменшує `Product.StockQuantity` на замовлену кількість.
9. Очищає кошик.
10. Зберігає замовлення, позиції, залишки та очищення кошика в одній транзакції.

Якщо будь-який крок до фіксації транзакції завершується помилкою, зміни замовлення, складу та кошика відкочуються.

### Важлива поведінка при нестачі товару

Кошик може показувати, що користувач запросив 5 одиниць, але зараз доступно лише 3. Це відображення не змінює збережене запитане значення.

Під час оформлення замовлення backend вимагає наявності всієї запитаної кількості. Якщо замовлено 5, а залишилося 3, замовлення не буде автоматично оформлене на 3 одиниці: API поверне `409 Conflict`. Користувач має змінити кількість у кошику та повторити оформлення.

### Успішна відповідь

Успішне створення повертає HTTP `201 Created`; замовлення міститься в `data` оболонки `RestResponse`.

```json
{
  "status": {
    "isOk": true,
    "code": 201,
    "message": "Created"
  },
  "meta": {
    "apiName": "Orders",
    "dataType": "application/json",
    "cacheTime": 0,
    "manipulations": ["POST"],
    "links": {
      "self": "/api/orders/my"
    }
  },
  "data": {
    "id": "00000000-0000-0000-0000-000000000200",
    "customerName": "Іван Іванов",
    "phoneNumber": "+380991234567",
    "city": "Одеса",
    "deliveryAddress": "Нова пошта, відділення 10",
    "comment": "Зателефонувати перед доставкою",
    "totalAmount": 18000.00,
    "status": "New",
    "createdAt": "2026-11-02T12:00:00Z",
    "updatedAt": "2026-11-02T12:00:00Z",
    "items": [
      {
        "id": "00000000-0000-0000-0000-000000000201",
        "productId": "00000000-0000-0000-0000-000000000001",
        "productName": "Приклад смартфона",
        "productSku": "PHONE-001",
        "unitPrice": 9000.00,
        "quantity": 2,
        "totalPrice": 18000.00
      }
    ]
  }
}
```

Значення в прикладі ілюстративні. `customerName` у відповіді формується з вхідного `fullName`.

Типові помилки:

- `400 Bad Request` — некоректні обов'язкові поля або помилка аргументів;
- `401 Unauthorized` — немає дійсного токена;
- `403 Forbidden` — роль не дозволяє оформлювати замовлення;
- `409 Conflict` — кошик порожній, товар неактивний або недостатньо залишку.

Помилки автоматичної перевірки DataAnnotations через `[ApiController]` можуть мати стандартний формат `ProblemDetails`, а не `RestResponse`.

## 2. Отримати власні замовлення

```http
GET {{baseUrl}}/api/orders/my
Authorization: Bearer {{userToken}}
```

Доступно лише ролі `User`. Backend бере `UserId` з JWT і повертає тільки замовлення цього користувача. Передати ID іншого користувача через запит неможливо.

Успішна відповідь — `200 OK`; `data` містить масив `OrderDto`. Список відсортований від новіших замовлень до старіших (`CreatedAt` за спаданням, далі `Id` за спаданням). Якщо замовлень немає, повертається порожній масив.

## 3. Отримати всі замовлення

```http
GET {{baseUrl}}/api/orders/admin
Authorization: Bearer {{managerToken}}
```

Доступно ролям `Manager` та `Admin`. Відповідь — `200 OK`, `data` містить масив усіх замовлень із позиціями, відсортований від новіших до старіших.

Поточна реалізація не має пагінації для цього endpoint-а.

## 4. Отримати деталі замовлення

```http
GET {{baseUrl}}/api/orders/admin/{{orderId}}
Authorization: Bearer {{managerToken}}
```

Доступно ролям `Manager` та `Admin`. Успіх — `200 OK` з одним `OrderDto` у `data`. Якщо замовлення не знайдено — `404 Not Found`.

Деталі містять контактні дані отримувача, адресу доставки, коментар, статус, суму й перелік позицій.

## 5. Змінити статус замовлення

```http
PUT {{baseUrl}}/api/orders/admin/{{orderId}}/status
Authorization: Bearer {{managerToken}}
Content-Type: application/json
```

Тіло запиту:

```json
{
  "status": "Processing"
}
```

Дозволені назви: `New`, `Processing`, `Completed`, `Cancelled`. Перевірка назви не враховує регістр. Числові значення enum не приймаються.

Успіх — `200 OK` з оновленим `OrderDto` у `data`.

Під час переходу в `Cancelled` backend у межах транзакції:

1. Блокує замовлення.
2. Перевіряє допустимість переходу.
3. Блокує товари, що входять до замовлення.
4. Повертає зарезервовану кількість кожного товару до `StockQuantity`.
5. Змінює статус і дату оновлення.
6. Зберігає зміни й фіксує транзакцію.

Повторний запит із тим самим статусом не повертає товар на склад повторно.

Типові помилки:

- `400 Bad Request` — відсутній або невідомий статус, порожній GUID;
- `401 Unauthorized` — токен відсутній, недійсний або прострочений;
- `403 Forbidden` — роль не `Manager` і не `Admin`;
- `404 Not Found` — замовлення не знайдено;
- `409 Conflict` — недопустимий перехід статусу або помилка відновлення залишку.

## 6. Структура OrderDto

```json
{
  "id": "ORDER_ID",
  "customerName": "Іван Іванов",
  "phoneNumber": "+380991234567",
  "city": "Одеса",
  "deliveryAddress": "Нова пошта, відділення 10",
  "comment": null,
  "totalAmount": 18000.00,
  "status": "New",
  "createdAt": "2026-11-02T12:00:00Z",
  "updatedAt": "2026-11-02T12:00:00Z",
  "items": [
    {
      "id": "ORDER_ITEM_ID",
      "productId": "PRODUCT_ID",
      "productName": "Приклад смартфона",
      "productSku": "PHONE-001",
      "unitPrice": 9000.00,
      "quantity": 2,
      "totalPrice": 18000.00
    }
  ]
}
```

`unitPrice` — остаточна ціна одиниці на момент оформлення замовлення, з урахуванням застосованої знижки. `productName` та `productSku` — знімки значень на момент покупки. Тому подальші зміни назви, SKU або ціни товару не змінюють історію замовлення.

## 7. Правила залишків та історії замовлень

- Оформлення замовлення зменшує `Product.StockQuantity` у тій самій транзакції, у якій створюється замовлення.
- Кошик очищується лише після успішного збереження замовлення та позицій.
- При скасуванні замовлення зарезервована кількість повертається на склад.
- Статуси `Completed` і `Cancelled` є кінцевими.
- Фізичне видалення товару, на який посилається позиція замовлення, заборонене зовнішнім ключем. У каталозі товар слід деактивувати, а не видаляти фізично.
- Зв'язок замовлення з Identity-користувачем налаштований із `DeleteBehavior.Restrict`; наявні замовлення перешкоджають фізичному видаленню відповідного облікового запису.
- Онлайн-оплата, інтеграція з перевізником і створення накладних цими endpoint-ами не реалізовані.

## 8. Перевірка через Postman

1. Увійдіть під користувачем `User` та отримайте JWT.
2. Додайте активний товар у кошик через `POST /api/cart/items`.
3. Перевірте кошик через `GET /api/cart`.
4. Оформіть замовлення через `POST /api/orders`.
5. Переконайтеся, що відповідь має HTTP `201`, кошик очищено, а складський залишок зменшився.
6. Виконайте `GET /api/orders/my` і переконайтеся, що замовлення присутнє.
7. Увійдіть під `Manager` і перевірте `GET /api/orders/admin` та `GET /api/orders/admin/{id}`.
8. Переведіть замовлення `New` → `Processing` → `Completed` і перевірте заборону подальшого переходу.
9. Оформіть інше замовлення та перевірте скасування `New` → `Cancelled` або `Processing` → `Cancelled`; залишок має відновитися один раз.
10. Перевірте, що `User` не має доступу до адміністративних endpoint-ів, а `Manager` не має доступу до endpoint-ів управління каталогом і користувачами.
