# Brands API — документація брендів

Документ описує фактичні маршрути `BrandsController` і відповідну поведінку `DataAccessor`: перегляд активних брендів, локалізовані назви й описи, отримання товарів бренду, створення та редагування, деактивацію й відновлення, а також завантаження та перегляд логотипів.

## Перед початком

У прикладах `{{baseUrl}}` — базова адреса запущеного API, наприклад `https://localhost:7001`. Використовуйте адресу, яку показує застосунок під час запуску.

Публічні GET-endpoint-и не потребують токена. Для створення, редагування, деактивації, відновлення бренду та завантаження логотипа потрібен JWT користувача з роллю `Admin`:

```http
Authorization: Bearer {{adminToken}}
```

Мова назви та опису залежить від поточної культури HTTP-запиту. Застосунок підтримує `uk-UA` та `en-US`; якщо перекладу для поточної культури немає, використовується `uk-UA`.

**Важливо:** роль `Admin` додає до GET-відповідей усі переклади активного бренду, але не відкриває доступ до неактивних брендів. Пошук за ID і за `slug`, як і список, повертає лише активні записи незалежно від ролі.

## Короткий список endpoint-ів

| Метод | URL | Доступ | Призначення |
|---|---|---|---|
| `GET` | `/api/brands` | Публічний | Список активних брендів |
| `GET` | `/api/brands/{id}` | Публічний | Отримати активний бренд за GUID |
| `GET` | `/api/brands/slug/{slug}` | Публічний | Отримати активний бренд за `slug` |
| `GET` | `/api/brands/{id}/products` | Публічний | Каталог активних товарів бренду з фільтрами та пагінацією |
| `POST` | `/api/brands` | `Admin` | Створити бренд |
| `PUT` | `/api/brands/{id}` | `Admin` | Оновити `slug` і переклади бренду |
| `DELETE` | `/api/brands/{id}` | `Admin` | Деактивувати бренд |
| `POST` | `/api/brands/{id}/restore` | `Admin` | Відновити бренд |
| `POST` | `/api/brands/{id}/logo` | `Admin` | Завантажити або замінити логотип активного бренду |
| `GET` | `/api/brands/images/{imageKey}` | Публічний | Отримати файл логотипа з локального сховища |

## Формат відповідей

Більшість endpoint-ів повертає `RestResponse`:

```json
{
  "status": {
    "isOk": true,
    "code": 200,
    "message": "OK"
  },
  "meta": {
    "apiName": "Brands",
    "dataType": "json/array",
    "cacheTime": 0
  },
  "data": []
}
```

Це скорочений приклад. `RestMeta` також може містити `links`, `manipulations` та `parameters`.

Є винятки:

- помилки автоматичної валідації `[ApiController]` можуть повертати `ProblemDetails`;
- `GET /api/brands/images/{imageKey}` повертає бінарний файл, а не JSON;
- формат помилки може відрізнятися від стандартної оболонки залежно від джерела помилки.

Клієнту слід орієнтуватися насамперед на HTTP-статус і не припускати, що всі відповіді мають однакове тіло.

## 1. Перегляд брендів

### Список активних брендів

```http
GET {{baseUrl}}/api/brands
```

Endpoint повертає всі активні бренди без пагінації та query-фільтрів. Сортування виконується за локалізованою назвою без урахування регістру; для відсутнього перекладу використовується український (`uk-UA`).

Приклад публічної відповіді:

```json
{
  "status": {
    "isOk": true,
    "code": 200,
    "message": "OK"
  },
  "meta": {
    "apiName": "Brands",
    "dataType": "json/array",
    "cacheTime": 0,
    "manipulations": ["GET"],
    "links": {
      "self": "/api/brands"
    }
  },
  "data": [
    {
      "id": "00000000-0000-0000-0000-000000000001",
      "name": "Samsung",
      "slug": "samsung",
      "description": "Електроніка та побутова техніка",
      "logoUrl": "/api/brands/images/a1b2c3d4e5f678901234567890abcdef.webp",
      "translations": []
    }
  ]
}
```

Для запиту без ролі `Admin` поле `translations` буде порожнім масивом. Якщо GET-запит виконує авторизований користувач із роллю `Admin`, у цьому полі повертається повна колекція перекладів активного бренду. Сам endpoint залишається публічним.

`logoUrl` може бути `null`, якщо логотип не заданий. Для локального ключа сховища API формує шлях `/api/brands/images/{imageKey}`. Якщо в старому записі збережено інше значення, зокрема зовнішню URL-адресу, воно повертається без зміни.

### Отримати бренд за ID

```http
GET {{baseUrl}}/api/brands/{{brandId}}
```

`brandId` — GUID бренду. Успішна відповідь повертає `BrandDto` у `data`. Якщо бренд відсутній або деактивований, повертається `404 Not Found`, у тому числі для `Admin`.

### Отримати бренд за slug

```http
GET {{baseUrl}}/api/brands/slug/samsung
```

`slug` — унікальне адресне ім'я бренду. Під час створення та оновлення воно обрізається по краях і переводиться в нижній регістр. Дозволені латинські літери, цифри та одиночні дефіси між групами символів. Максимальна довжина — 150 символів.

Порожній або довший за 150 символів `slug` повертає `400 Bad Request`. Якщо активного бренду з таким значенням немає, повертається `404 Not Found`. Неактивний бренд за `slug` також недоступний адміністратору через цей endpoint.

## 2. Переклади бренду

Сутність `Brand` не зберігає `Name` і `Description` безпосередньо. Вони зберігаються в окремих записах `BrandTranslation`. Підтримуються локалі `uk-UA` та `en-US`.

Формат перекладу:

```json
{
  "cultureCode": "uk-UA",
  "name": "Samsung",
  "description": "Електроніка та побутова техніка"
}
```

| Поле | Правило |
|---|---|
| `cultureCode` | Обов'язкове; підтримуються `uk-UA` та `en-US`; дублікати локалі в одному запиті заборонені |
| `name` | Обов'язкове після обрізання пробілів; від 1 до 150 символів |
| `description` | Необов'язкове; максимум 1000 символів; може бути `null` |

Під час створення бренд повинен містити переклад `uk-UA`. Переклад `en-US` можна додати одразу або пізніше. У відповіді звичайного користувача `name` і `description` представляють переклад поточної культури з fallback на `uk-UA`.

Унікальність забезпечується для пари «бренд + культура». Для одного бренду не можна зберегти два переклади з однаковим `cultureCode`.

## 3. Отримати товари бренду

```http
GET {{baseUrl}}/api/brands/{{brandId}}/products
```

Endpoint повертає активні товари, пов'язані з указаним активним брендом. Ідентифікатор бренду завжди береться з маршруту: значення `brandId` з query-параметрів не може перевизначити його. Додаткові фільтри каталогу можна комбінувати з маршрутом бренду.

### Параметри каталогу

| Параметр | Приклад | Поведінка |
|---|---|---|
| `page` | `page=2` | Номер сторінки, починаючи з 1; має бути не менше 1 |
| `pageSize` | `pageSize=20` | Кількість товарів на сторінці: від 1 до 100 |
| `search` | `search=phone` | Пошук за SKU, назвою або описом; максимум 100 символів |
| `minPrice` | `minPrice=100` | Мінімальна ціна включно; не може бути від'ємною |
| `maxPrice` | `maxPrice=1000` | Максимальна ціна включно; не може бути від'ємною |
| `categoryId` | `categoryId={{categoryId}}` | Додатковий фільтр за GUID активної категорії |
| `inStock` | `inStock=true` | `true` — `StockQuantity > 0`; `false` — `StockQuantity <= 0` |
| `sortBy` | `sortBy=price` | `name`, `price` або `createdAt` |
| `sortDirection` | `sortDirection=desc` | `asc` або `desc` |

Значення за замовчуванням: `page=1`, `pageSize=12`, `sortBy=name`, `sortDirection=asc`. Каталог також відхиляє offset, що перевищує `Int32.MaxValue`, пошук довший за 100 символів, від'ємні ціни, `minPrice > maxPrice`, невідоме поле сортування та невідомий напрямок.

Приклад запиту:

```http
GET {{baseUrl}}/api/brands/{{brandId}}/products?page=2&pageSize=20&minPrice=100&maxPrice=1000&inStock=true&sortBy=price&sortDirection=desc
```

Успішна відповідь містить масив товарів у `data`, пагінацію в `meta.pagination` та ідентифікатор бренду й налаштування сортування в `meta.parameters`:

```json
{
  "status": {
    "isOk": true,
    "code": 200,
    "message": "OK"
  },
  "meta": {
    "apiName": "BrandProducts",
    "dataType": "json/array",
    "cacheTime": 0,
    "manipulations": ["GET"],
    "links": {
      "self": "/api/brands/00000000-0000-0000-0000-000000000001/products"
    },
    "pagination": {
      "page": 2,
      "pageSize": 20,
      "totalPages": 2,
      "totalItems": 35
    },
    "parameters": {
      "brandId": "00000000-0000-0000-0000-000000000001",
      "sortBy": "price",
      "sortDirection": "desc"
    }
  },
  "data": []
}
```

Значення в прикладі наведені для ілюстрації. Некоректні параметри повертають `400 Bad Request`. Якщо бренд відсутній або деактивований, маршрут повертає `404 Not Found`.

Товари з неактивним брендом не повертаються через фільтр цього бренду. При цьому сам товар, якщо він активний, може відображатися в загальному каталозі без назви неактивного бренду, оскільки фільтрація товарів загалом не обмежується лише товарами з активним брендом.

## 4. Створити бренд

Потрібен JWT адміністратора.

```http
POST {{baseUrl}}/api/brands
Authorization: Bearer {{adminToken}}
Content-Type: application/json
```

**Актуальна структура запиту:** `BrandCreateRequest` містить `slug` і `translations`. `name` та `description` передаються всередині кожного перекладу, а не на верхньому рівні.

```json
{
  "slug": "samsung",
  "translations": [
    {
      "cultureCode": "uk-UA",
      "name": "Samsung",
      "description": "Електроніка та побутова техніка"
    },
    {
      "cultureCode": "en-US",
      "name": "Samsung",
      "description": "Electronics and home appliances"
    }
  ]
}
```

Правила:

- `slug` — обов'язковий, від 1 до 150 символів; дозволені латинські літери, цифри та дефіси між групами символів;
- `translations` — обов'язковий непорожній список;
- кожен переклад повинен містити підтримуваний `cultureCode` і непорожню назву;
- переклад `uk-UA` обов'язковий;
- `description` — необов'язкове, максимум 1000 символів;
- повторювати одну локаль у `translations` не можна.

`slug` обрізається і зберігається в нижньому регістрі. Він має бути унікальним серед усіх брендів, включно з деактивованими. `name`, `description` і `logoUrl` на верхньому рівні запиту не використовуються; логотип завантажується окремо.

Успіх — `201 Created`, `data` містить створений `BrandDto` з усіма перекладами. Конфлікт унікального `slug` — `409 Conflict`; некоректні дані або переклади — `400 Bad Request`.

Приклад скороченої відповіді:

```json
{
  "status": {
    "isOk": true,
    "code": 201,
    "message": "Created"
  },
  "meta": {
    "apiName": "Brand",
    "dataType": "json/object",
    "manipulations": ["GET"],
    "links": {
      "parent": "/api/brands",
      "self": "/api/brands/00000000-0000-0000-0000-000000000001"
    }
  },
  "data": {
    "id": "00000000-0000-0000-0000-000000000001",
    "name": "Samsung",
    "slug": "samsung",
    "description": "Електроніка та побутова техніка",
    "logoUrl": null,
    "translations": [
      {
        "cultureCode": "uk-UA",
        "name": "Samsung",
        "description": "Електроніка та побутова техніка"
      }
    ]
  }
}
```

## 5. Оновити бренд

Потрібен JWT адміністратора.

```http
PUT {{baseUrl}}/api/brands/{{brandId}}
Authorization: Bearer {{adminToken}}
Content-Type: application/json
```

Приклад тіла запиту:

```json
{
  "slug": "samsung-electronics",
  "translations": [
    {
      "cultureCode": "uk-UA",
      "name": "Samsung Electronics",
      "description": "Оновлений опис бренду"
    }
  ]
}
```

Правила:

- `slug` має відповідати формату створення та бути унікальним серед інших брендів;
- `translations` має містити щонайменше один переклад;
- під час оновлення український переклад не є обов'язковим у поточному запиті;
- наявні переклади оновлюються за `cultureCode`, нові локалі додаються;
- локалі, не передані в запиті, залишаються в базі й не видаляються;
- повтори `cultureCode` заборонені;
- `logoUrl` та `isActive` не є полями `BrandUpdateRequest`.

Адміністратор може редагувати бренд за наявним ID, навіть якщо він деактивований. Сам `PUT` не активує бренд. Щоб змінити логотип, використовуйте окремий endpoint.

Успіх — `200 OK`, `data` містить адміністративне представлення бренду з колекцією перекладів. `404 Not Found` — бренд з таким ID відсутній; `400 Bad Request` — некоректний запит; `409 Conflict` — `slug` вже використовується.

## 6. Деактивувати та відновити бренд

Деактивація є м'якою: запис залишається в БД, а `IsActive` встановлюється в `false`. Фізичного видалення бренду через цей API немає.

### Деактивація

```http
DELETE {{baseUrl}}/api/brands/{{brandId}}
Authorization: Bearer {{adminToken}}
```

Успіх — `200 OK` з повідомленням `Brand deactivated successfully.` Якщо бренд не існує або вже деактивований — `404 Not Found`.

Деактивація не обнуляє `BrandId` у пов'язаних товарах і не видаляє логотип. У публічному представленні товару назва неактивного бренду не повертається. Фільтр товарів за деактивованим брендом повертає `404 Not Found`.

### Відновлення

```http
POST {{baseUrl}}/api/brands/{{brandId}}/restore
Authorization: Bearer {{adminToken}}
```

Успіх — `200 OK` з повідомленням `Brand restored successfully.` Якщо бренд відсутній або вже активний — `404 Not Found`. Після відновлення він знову з'являється у публічному списку; збережений логотип залишається прив'язаним до бренду.

## 7. Завантажити або замінити логотип

Потрібен JWT адміністратора. Логотип передається через `multipart/form-data`.

```http
POST {{baseUrl}}/api/brands/{{brandId}}/logo
Authorization: Bearer {{adminToken}}
```

У Postman відкрийте **Body → form-data**, додайте поле `file` типу **File** та виберіть зображення. Не задавайте вручну `Content-Type` із boundary: Postman сформує його сам.

Спільний `LocalStorageService` приймає JPEG, PNG та WEBP із відповідними MIME-типами (`image/jpeg`, `image/png`, `image/webp`). Налаштовано максимальний розмір вхідного файла **5 MiB** і ліміт **12 000 000 пікселів**. Порожні, невалідні, невідповідні заявленому MIME-типу та анімовані зображення відхиляються. Перед збереженням зображення декодується та перекодовується у відповідний формат; оригінальне ім'я завантаженого файла не використовується як ім'я файла у сховищі.

Успіх — `200 OK`:

```json
{
  "status": {
    "isOk": true,
    "code": 200,
    "message": "OK"
  },
  "meta": {
    "apiName": "BrandLogo",
    "dataType": "application/json",
    "manipulations": ["POST"],
    "links": {
      "parent": "/api/brands",
      "logo": "/api/brands/images/a1b2c3d4e5f678901234567890abcdef.webp"
    }
  },
  "data": {
    "brandId": "00000000-0000-0000-0000-000000000001",
    "logoKey": "a1b2c3d4e5f678901234567890abcdef.webp",
    "logoUrl": "/api/brands/images/a1b2c3d4e5f678901234567890abcdef.webp"
  }
}
```

Ключ генерує сервіс сховища, він має формат GUID без дефісів плюс розширення `.jpg`, `.png` або `.webp`. `logoKey` — ключ файла у сховищі; `logoUrl` — шлях, за яким його можна отримати.

Endpoint завантаження працює лише з активним брендом. Якщо бренд відсутній або деактивований, новий файл видаляється best-effort, а API повертає `404 Not Found`. Відсутній або порожній файл, непідтримуваний MIME-тип чи помилка перевірки зображення повертає `400 Bad Request`. Неочікувана помилка файлової системи або БД може завершитися `500 Internal Server Error`.

Повторне завантаження замінює ключ логотипа в БД. Після успішного оновлення контролер намагається видалити попередній файл, якщо старе значення відповідає формату ключа локального сховища. Помилка очищення старого файла записується в журнал і не скасовує успішне оновлення. Попереднє зовнішнє URL-значення не видаляється локальним сервісом.

## 8. Отримати файл логотипа

```http
GET {{baseUrl}}/api/brands/images/{{imageKey}}
```

Endpoint публічний і повертає бінарний файл із відповідним `Content-Type`, а не JSON. Підтримуються `.jpg`, `.png` та `.webp`.

Приклад повної адреси:

```text
https://localhost:<port>/api/brands/images/a1b2c3d4e5f678901234567890abcdef.webp
```

Можна використовувати `logoUrl` із відповіді бренду або `logoKey` з відповіді завантаження. Непідтримуване розширення або некоректний ключ повертають `400 Bad Request`; відсутній файл — `404 Not Found`.

Endpoint читає лише файли локального сховища. Якщо старий запис бренду містить зовнішню URL-адресу, ця адреса повертається в `logoUrl` без змін — для неї не слід використовувати `/api/brands/images/{imageKey}`.

## 9. HTTP-статуси

| Код | Значення |
|---|---|
| `200 OK` | Операція успішна; включно з оновленням, деактивацією, відновленням і завантаженням логотипа |
| `201 Created` | Бренд створено |
| `400 Bad Request` | Некоректні поля, локалі, `slug`, параметри каталогу або зображення |
| `401 Unauthorized` | Для захищеної операції не надано дійсний JWT |
| `403 Forbidden` | JWT дійсний, але користувач не має ролі `Admin` |
| `404 Not Found` | Бренд відсутній/неактивний, або локальний файл не знайдено |
| `409 Conflict` | `slug` уже використовується |
| `500 Internal Server Error` | Неочікувана помилка сервера або файлової системи |

Формат тіла помилки залежить від endpoint-а. Помилки бізнес-логіки зазвичай повертаються в `RestResponse`; автоматична валідація DTO може повертати `ProblemDetails`; endpoint читання логотипа повертає сам файл при успіху.

## 10. Перевірка через Postman

1. Увійдіть під адміністратором і скопіюйте `accessToken`.
2. Виконайте `GET /api/brands` без токена: має повернутися список активних брендів.
3. Виконайте GET-запит із токеном Admin і перевірте, що `translations` містить усі доступні переклади активних брендів.
4. Створіть бренд через `POST /api/brands`, передавши `slug` та масив `translations` із перекладом `uk-UA`.
5. Оновіть бренд через `PUT /api/brands/{id}` лише з `en-US` і переконайтеся, що раніше збережений `uk-UA` не видалився.
6. Завантажте логотип через `multipart/form-data`, а потім відкрийте повернутий `logoUrl`.
7. Перевірте, що повторний `slug` повертає `409 Conflict`, а повторна локаль у `translations` — `400 Bad Request`.
8. Деактивуйте бренд і перевірте `GET /api/brands/{id}` та `/api/brands/{id}/products`: обидва маршрути мають повертати `404 Not Found` для цього бренду.
9. Відновіть бренд і перевірте, що він знову доступний у публічному списку.
10. Спробуйте адміністративні операції з токеном ролі `User`: очікується `403 Forbidden`.
