# Products API — документація каталогу товарів

Документ описує фактичні маршрути `ProductsController` і відповідну поведінку `DataAccessor`: каталог, отримання товару, переклади, характеристики, зображення, деактивацію та відновлення.

## Перед початком

У прикладах `{{baseUrl}}` — базова адреса запущеного API, наприклад `https://localhost:7001`. Використовуйте адресу, яку показує застосунок під час запуску.

Публічні операції читання не потребують токена. Створення, редагування, деактивація та відновлення товарів, а також керування зображеннями й характеристиками доступні лише користувачам із роллю `Admin`.

Для адміністративних запитів передавайте JWT:

```http
Authorization: Bearer {{adminToken}}
```

Мова назв, описів і характеристик визначається поточною культурою HTTP-запиту. У застосунку підтримуються `uk-UA` та `en-US`; якщо перекладу для поточної мови немає, використовується `uk-UA`.

## Короткий список endpoint-ів

| Метод | URL | Доступ | Призначення |
|---|---|---|---|
| `GET` | `/api/products` | Публічний | Каталог із пошуком, фільтрами, сортуванням і пагінацією |
| `GET` | `/api/products/{id}` | Публічний; Admin має розширений доступ | Отримати товар за GUID |
| `GET` | `/api/products/slug/{slug}` | Публічний; Admin також може отримати неактивний товар | Отримати товар за slug |
| `GET` | `/api/products/images/{imageKey}` | Публічний | Отримати файл зображення |
| `GET` | `/api/products/{productId}/images` | Публічний; Admin також бачить зображення неактивного товару | Отримати зображення товару |
| `POST` | `/api/products` | `Admin` | Створити товар |
| `PUT` | `/api/products/{id}` | `Admin` | Оновити товар, категорії, переклади й набір характеристик |
| `DELETE` | `/api/products/{id}` | `Admin` | Деактивувати товар |
| `POST` | `/api/products/{id}/restore` | `Admin` | Відновити неактивний товар |
| `POST` | `/api/products/{id}/images` | `Admin` | Завантажити зображення |
| `PUT` | `/api/products/{productId}/images/{imageId}` | `Admin` | Змінити головне зображення та порядок |
| `DELETE` | `/api/products/{productId}/images/{imageId}` | `Admin` | Видалити зображення та, за можливості, його локальний файл |
| `GET` | `/api/products/{productId}/specifications` | Публічний; Admin також бачить неактивний товар і всі переклади | Отримати характеристики |
| `GET` | `/api/products/{productId}/specifications/{specificationId}` | Публічний; Admin має розширений доступ | Отримати одну характеристику |
| `POST` | `/api/products/{productId}/specifications` | `Admin` | Створити характеристику |
| `PUT` | `/api/products/{productId}/specifications/{specificationId}` | `Admin` | Оновити характеристику |
| `DELETE` | `/api/products/{productId}/specifications/{specificationId}` | `Admin` | Остаточно видалити характеристику |

## Формат відповідей

Більшість endpoint-ів повертає `RestResponse`:

```json
{
  "status": {
    "isOk": true,
    "code": 200,
    "message": "OK"
  },
  "meta": {
    "apiName": "Products",
    "dataType": "json/array",
    "cacheTime": 0
  },
  "data": []
}
```

Це скорочений приклад. `RestMeta` може також містити `links`, `pagination` і `parameters`.

Є винятки:

- `POST /api/products/{id}/images` повертає звичайний JSON-об'єкт без `RestResponse`.
- `GET /api/products/images/{imageKey}` повертає бінарний файл, а не JSON.
- Частина помилок файлового endpoint-а також повертається у звичайному JSON.
- Помилки автоматичної валідації `[ApiController]` можуть мати формат `ProblemDetails`, а не `RestResponse`.

Клієнт має орієнтуватися насамперед на HTTP-статус, а не припускати однакову JSON-оболонку для всіх відповідей.

## 1. Перегляд каталогу

```http
GET {{baseUrl}}/api/products?page=1&pageSize=12&sortBy=name&sortDirection=asc
```

Каталог містить лише активні товари. Фільтри бренду й категорії враховують лише активні бренди та категорії.

### Параметри запиту

| Параметр | Приклад | Поведінка |
|---|---|---|
| `page` | `page=2` | Номер сторінки, починаючи з 1; значення має бути не менше 1 |
| `pageSize` | `pageSize=20` | Кількість товарів на сторінці: від 1 до 100 |
| `search` | `search=phone` | Пошук за SKU, назвою або описом у поточній локалі та `uk-UA`; максимум 100 символів |
| `minPrice` | `minPrice=100` | Мінімальна ціна включно; не може бути від'ємною |
| `maxPrice` | `maxPrice=1000` | Максимальна ціна включно; не може бути від'ємною |
| `brandId` | `brandId={{brandId}}` | Фільтр за GUID активного бренду |
| `categoryId` | `categoryId={{categoryId}}` | Фільтр за GUID активної категорії |
| `inStock` | `inStock=true` | `true` — `StockQuantity > 0`; `false` — `StockQuantity <= 0` |
| `sortBy` | `sortBy=price` | Поле сортування: `name`, `price` або `createdAt` |
| `sortDirection` | `sortDirection=desc` | Напрямок сортування: `asc` або `desc` |

`minPrice` не може перевищувати `maxPrice`. Номер сторінки також відхиляється, якщо розрахований offset перевищує `Int32.MaxValue`.

Значення за замовчуванням: `page=1`, `pageSize=12`, `sortBy=name`, `sortDirection=asc`. Контролер приймає лише `name`, `price`, `createdAt` для `sortBy` та `asc`, `desc` для `sortDirection`; порожні або невідомі значення повертають `400 Bad Request`.

Пошук виконується за SKU та перекладами товару: спочатку за поточною культурою, а також за українським перекладом. Назви товарів сортуються за поточною культурою з fallback на `uk-UA`. Для однакових значень використовується ID товару як додатковий критерій.

Приклад:

```http
GET {{baseUrl}}/api/products?search=phone&minPrice=100&maxPrice=1000&inStock=true&page=1&pageSize=20&sortBy=price&sortDirection=desc
```

Успішна відповідь містить масив товарів у `data`. Інформація про сторінки міститься в `meta.pagination`, а застосовані параметри сортування — у `meta.parameters`.

Приклад скороченої відповіді:

```json
{
  "status": {
    "isOk": true,
    "code": 200,
    "message": "OK"
  },
  "meta": {
    "apiName": "Products",
    "dataType": "json/array",
    "pagination": {
      "page": 1,
      "pageSize": 12,
      "totalPages": 3,
      "totalItems": 29
    },
    "parameters": {
      "sortBy": "price",
      "sortDirection": "desc"
    }
  },
  "data": [
    {
      "id": "00000000-0000-0000-0000-000000000001",
      "sku": "PHONE-001",
      "name": "Приклад смартфона",
      "slug": "pryklad-smartfona",
      "price": 499.99,
      "stockQuantity": 7,
      "brandName": "Приклад бренду",
      "primaryImageUrl": "/api/products/images/a1b2c3d4e5f678901234567890abcdef.webp",
      "categories": ["Смартфони"],
      "activePromotion": null
    }
  ]
}
```

`activePromotion` містить результат розрахунку застосовної активної акції або `null`, якщо для товару немає відповідної акції. Якщо поле не `null`, `ProductPromotionPriceDto` містить `promotionId`, `title`, `slug`, `discountType`, `discountValue`, `originalPrice`, `discountAmount` і `discountedPrice`.

Некоректні параметри, зокрема `page=0`, `pageSize=200`, від'ємна ціна, `minPrice > maxPrice`, пошук довший за 100 символів або невідоме поле сортування, повертають `400 Bad Request`.

## 2. Отримати один товар

За ID:

```http
GET {{baseUrl}}/api/products/{{productId}}
```

За slug:

```http
GET {{baseUrl}}/api/products/slug/pryklad-smartfona
```

`productId` — GUID товару. `slug` — унікальне адресне ім'я товару довжиною до 150 символів згідно з перевіркою контролера.

Публічний запит повертає лише активний товар. Адміністратор може отримати також неактивний товар — як за ID, так і за slug. Адміністративна відповідь містить усі збережені переклади товару та характеристик; публічна відповідь містить локалізовані значення. У DTO публічного детального запиту властивість `translations` товару та властивість `translations` кожної характеристики залишаються порожніми масивами; адміністративне представлення заповнює їх усіма збереженими перекладами.

Приклад скороченого об'єкта товару:

```json
{
  "id": "00000000-0000-0000-0000-000000000001",
  "sku": "PHONE-001",
  "name": "Приклад смартфона",
  "slug": "pryklad-smartfona",
  "description": "Опис товару",
  "isActive": true,
  "translations": [],
  "price": 499.99,
  "stockQuantity": 7,
  "brandName": "Приклад бренду",
  "categories": ["Смартфони"],
  "images": [
    {
      "id": "00000000-0000-0000-0000-000000000020",
      "imageUrl": "/api/products/images/a1b2c3d4e5f678901234567890abcdef.webp",
      "isPrimary": true,
      "sortOrder": 0
    }
  ],
  "specifications": [
    {
      "id": "00000000-0000-0000-0000-000000000010",
      "name": "Колір",
      "value": "Чорний",
      "sortOrder": 0,
      "translations": []
    }
  ],
  "activePromotion": null
}
```

Якщо товар не знайдено або він неактивний для публічного запиту, повертається `404 Not Found`.

## 3. Переклади товару

Товар зберігає переклади окремо від основної сутності. Під час створення потрібен принаймні український переклад (`uk-UA`). Додатково підтримується англійський (`en-US`). Інші коди локалей відхиляються.

Формат перекладу:

```json
{
  "cultureCode": "uk-UA",
  "name": "Приклад смартфона",
  "description": "Опис товару"
}
```

Правила DTO та бізнес-логіки:

| Поле | Правило |
|---|---|
| `cultureCode` | Обов'язковий; лише `uk-UA` або `en-US`; без повторів у межах одного товару |
| `name` | Обов'язкове після обрізання пробілів; максимум 150 символів |
| `description` | Обов'язкове поле запиту; максимум 5000 символів. `DataAccessor` обрізає пробіли та має fallback для `null`, але API-валідація DTO вимагає передати поле |

Якщо поточна локаль не має перекладу, API використовує `uk-UA`. Під час створення український переклад обов'язковий. Під час оновлення дозволено передати переклад лише однієї підтримуваної локалі: відсутні в запиті локалі не видаляються, а зберігають попередні значення. На рівні DTO поле `description` позначене `[Required]`, тому в HTTP-запиті його потрібно передавати, навіть попри fallback для `null` у `DataAccessor`.

## 4. Створити товар

Потрібен JWT користувача з роллю `Admin`.

```http
POST {{baseUrl}}/api/products
Authorization: Bearer {{adminToken}}
Content-Type: application/json
```

Приклад тіла відповідно до властивостей, які використовує поточний `DataAccessor`:

```json
{
  "sku": "PHONE-001",
  "slug": "pryklad-smartfona",
  "price": 499.99,
  "stockQuantity": 7,
  "brandId": null,
  "categoryIds": [],
  "translations": [
    {
      "cultureCode": "uk-UA",
      "name": "Приклад смартфона",
      "description": "Опис товару"
    },
    {
      "cultureCode": "en-US",
      "name": "Sample smartphone",
      "description": "Product description"
    }
  ],
  "specifications": [
    {
      "sortOrder": 0,
      "translations": [
        {
          "cultureCode": "uk-UA",
          "name": "Колір",
          "value": "Чорний"
        },
        {
          "cultureCode": "en-US",
          "name": "Color",
          "value": "Black"
        }
      ]
    }
  ]
}
```

`name` і `description` більше не передаються безпосередньо на верхньому рівні товару. Вони знаходяться всередині `translations`. Так само `name` і `value` характеристики знаходяться всередині її `translations`.

Правила бізнес-логіки:

- `sku` обрізається від пробілів по краях; значення має бути унікальним.
- `slug` обрізається та переводиться в нижній регістр; значення має бути унікальним.
- `brandId` може бути `null`; якщо заданий, бренд повинен існувати та бути активним.
- `categoryIds` — список GUID без повторів; кожна категорія повинна існувати та бути активною. Порожній список дозволений.
- `translations` — непорожній список; український переклад обов'язковий.
- `specifications` не може бути `null`; порожній список дозволяє створити товар без характеристик.
- Кожна характеристика повинна мати непорожні переклади; під час створення український переклад обов'язковий.
- `sortOrder` характеристики не може бути від'ємним.
- Назви характеристик не можуть повторюватися в межах одного товару для тієї самої локалі без урахування регістру.

Для перекладів характеристик `name` має максимум 150 символів, `value` — максимум 1000 символів. Дозволені локалі — `uk-UA` та `en-US`.

Успіх — `201 Created`. Дублікат SKU/slug або конфлікт унікального значення повертає `409 Conflict`; некоректні переклади, категорії, бренд чи характеристики — `400 Bad Request`.

DTO також перевіряє основні поля до виклику `DataAccessor`: `sku` — обов'язковий, 1–100 символів; `slug` — обов'язковий, 1–150 символів; `price` — від `0.01` до `999999999`; `stockQuantity` — ціле число від `0` до `2147483647`. Для `translations` потрібен непорожній список. Кожен переклад має містити `cultureCode` довжиною до 10 символів, `name` довжиною 1–150 символів і обов'язковий `description` довжиною до 5000 символів. Бізнес-логіка додатково перевіряє підтримувану локаль, український переклад під час створення, унікальність SKU/slug, існування активного бренду та категорій і переклади характеристик.

Після створення API повертає адміністративне представлення товару, включно з колекціями перекладів.

## 5. Оновити товар

Потрібен JWT адміністратора.

```http
PUT {{baseUrl}}/api/products/{{productId}}
Authorization: Bearer {{adminToken}}
Content-Type: application/json
```

Приклад:

```json
{
  "sku": "PHONE-001",
  "slug": "pryklad-smartfona",
  "price": 459.99,
  "stockQuantity": 10,
  "brandId": null,
  "categoryIds": [],
  "translations": [
    {
      "cultureCode": "uk-UA",
      "name": "Оновлений смартфон",
      "description": "Оновлений опис"
    }
  ],
  "specifications": [
    {
      "id": "00000000-0000-0000-0000-000000000010",
      "sortOrder": 0,
      "translations": [
        {
          "cultureCode": "uk-UA",
          "name": "Колір",
          "value": "Синій"
        }
      ]
    },
    {
      "sortOrder": 1,
      "translations": [
        {
          "cultureCode": "uk-UA",
          "name": "Пам'ять",
          "value": "256 GB"
        }
      ]
    }
  ]
}
```

`PUT` оновлює основні поля товару та синхронізує повний набір категорій і характеристик:

- `categoryIds` — повний бажаний список категорій. Категорії, відсутні в запиті, від'єднуються; нові додаються.
- `specifications` — повний бажаний список характеристик. Наявна характеристика оновлюється за `id`; характеристика без `id` створюється; характеристики, чиї ID не передані, видаляються. Оскільки властивості `categoryIds` і `specifications` ініціалізовані порожніми списками, пропущені в `PUT` поля після десеріалізації також можуть бути порожніми: передавайте обидва поля явно, інакше можна від'єднати всі категорії та видалити всі характеристики.
- `id` характеристики має належати цьому товару. Чужий або невідомий ID повертає `400 Bad Request`.
- Один і той самий ID характеристики не можна передавати двічі.
- Порожній `categoryIds` від'єднує всі категорії. Порожній `specifications` видаляє всі характеристики.
- `specifications: null` відхиляється.
- Переклади товару та характеристик оновлюються за `cultureCode`: наявні локалі оновлюються, відсутні додаються. Локалі, яких немає в запиті, не видаляються.
- Для оновлення існуючої характеристики український переклад не обов'язковий у поточному запиті, оскільки попередні переклади зберігаються. Для нової характеристики український переклад обов'язковий.
- `isActive` цим endpoint-ом не змінюється. Деактивація та відновлення виконуються окремими endpoint-ами. Адміністратор може оновлювати також неактивний товар: метод шукає його лише за ID, без фільтра `IsActive`.

DTO для оновлення встановлює такі самі межі: `sku` — 1–100 символів, `slug` — 1–150, `price` — від `0.01` до `999999999`, `stockQuantity` — від `0` до `2147483647`. `translations` має містити щонайменше один переклад; в кожному перекладі `cultureCode` — до 10 символів, `name` — 1–150 символів, `description` — обов'язковий, до 5000 символів. Український переклад не обов'язковий для всього запиту оновлення, але наявні переклади з інших локалей зберігаються.

Успіх — `200 OK`; товар не знайдено — `404 Not Found`; некоректні дані — `400 Bad Request`; конфлікт унікальності SKU, slug або перекладів характеристик — `409 Conflict`.

**Важливо:** у попередній версії документації було написано, що характеристики під час оновлення зіставляються за назвою. Це не відповідає коду: зіставлення існуючих характеристик виконується за `id`.

## 6. Деактивувати та відновити товар

### Деактивація

```http
DELETE {{baseUrl}}/api/products/{{productId}}
Authorization: Bearer {{adminToken}}
```

Це soft delete: запис товару залишається в базі, а `IsActive` змінюється на `false`. Пов'язані зображення, характеристики, категорії та історичні посилання не видаляються.

Успіх — `200 OK` з повідомленням `Product deactivated successfully.` Повторна деактивація або відсутній товар повертає `404 Not Found`.

### Відновлення

```http
POST {{baseUrl}}/api/products/{{productId}}/restore
Authorization: Bearer {{adminToken}}
```

Успіх — `200 OK` з повідомленням `Product restored successfully.` Відсутній або вже активний товар повертає `404 Not Found`.

Після відновлення товар знову з'являється в публічному каталозі, якщо він відповідає іншим фільтрам. Неактивні бренд або категорії не активуються автоматично; їхні назви не потраплять у публічне представлення товару, доки самі бренд/категорії залишаються неактивними.

## 7. Завантажити зображення товару

Потрібен JWT адміністратора. Передається `multipart/form-data`:

```http
POST {{baseUrl}}/api/products/{{productId}}/images
Authorization: Bearer {{adminToken}}
Content-Type: multipart/form-data
```

Поля форми:

| Поле | Тип | Обов'язковість | Опис |
|---|---|---|---|
| `file` | File | Так | Файл зображення |
| `isPrimary` | Text/Boolean | Ні | Чи зробити зображення головним; за замовчуванням `false` |
| `sortOrder` | Text/Integer | Ні | Порядок відображення; за замовчуванням `0`, від'ємні значення заборонені |

У Postman виберіть **Body → form-data**, додайте `file` із типом **File**, а за потреби — `isPrimary` і `sortOrder` типу **Text**. Не задавайте вручну boundary для `multipart/form-data`; Postman сформує його сам.

Якщо `isPrimary=true`, інші зображення товару в межах цієї операції втрачають статус головного. Якщо `false`, поточний головний статус інших зображень не змінюється. Код не гарантує, що в кожного товару із зображеннями обов'язково буде рівно одне головне зображення.

Успіх повертає `200 OK` і звичайний JSON без `RestResponse`:

```json
{
  "productId": "00000000-0000-0000-0000-000000000001",
  "imageId": "00000000-0000-0000-0000-000000000020",
  "imageKey": "a1b2c3d4e5f678901234567890abcdef.webp",
  "imageUrl": "/api/products/images/a1b2c3d4e5f678901234567890abcdef.webp",
  "isPrimary": true,
  "sortOrder": 0
}
```

`imageId` використовується для редагування та видалення запису. `imageKey` — ключ файла у сховищі. `imageUrl` — готовий відносний шлях до публічного endpoint-а читання зображення.

Контролер повертає `400 Bad Request`, якщо файл відсутній/порожній або `sortOrder` від'ємний. `404 Not Found` — якщо товару немає. Налаштування з `appsettings.json`: `RootPath = LocalStorage/Files`, `MaxFileSizeBytes = 5242880` (5 MiB), `MaxImagePixels = 12000000` (12 мільйонів пікселів). `LocalStorageService` приймає лише MIME-типи `image/jpeg`, `image/png` та `image/webp`; фактичний формат декодованого файла має збігатися із заявленим `Content-Type`. Сервіс обмежує розмір вхідного файла та нормалізованого результату 5 MiB, перевіряє розміри до декодування й після нього, відхиляє анімовані зображення (`FrameCount != 1`) і повторно кодує файл, прибираючи початкові метадані. Розширення та ключ генеруються сервером (`.jpg`, `.png` або `.webp`; ключ має формат GUID без дефісів плюс розширення). Відхилення даних через `InvalidDataException` повертає `400 Bad Request`; помилки файлової системи під час збереження — `500 Internal Server Error`.

Файл спочатку зберігається у файловому сховищі, потім створюється запис у БД. Якщо товар не знайдений або запис у БД не вдається зберегти, контролер намагається видалити щойно завантажений файл. Якщо помилка БД виникла під час збереження, вона повторно викидається після спроби очищення та обробляється загальним middleware.

## 8. Отримати список зображень

```http
GET {{baseUrl}}/api/products/{{productId}}/images
```

Публічний запит доступний лише для активного товару. Admin із валідним JWT також може отримати зображення неактивного товару.

Успішна відповідь — `200 OK`, масив `ProductImageDto` у `data`. Сортування: `IsPrimary` за спаданням, `SortOrder` за зростанням, потім `Id`.

```json
{
  "status": {
    "isOk": true,
    "code": 200,
    "message": "OK"
  },
  "meta": {
    "apiName": "ProductImages",
    "dataType": "json/array",
    "cacheTime": 0,
    "manipulations": ["GET"],
    "links": {
      "parent": "/api/products",
      "self": "/api/products/00000000-0000-0000-0000-000000000001/images"
    }
  },
  "data": [
    {
      "id": "00000000-0000-0000-0000-000000000020",
      "imageUrl": "/api/products/images/a1b2c3d4e5f678901234567890abcdef.webp",
      "isPrimary": true,
      "sortOrder": 0
    }
  ]
}
```

Якщо товар відсутній або недоступний для публічного запиту, повертається `404 Not Found`.

## 9. Змінити параметри зображення

Потрібен JWT адміністратора.

```http
PUT {{baseUrl}}/api/products/{{productId}}/images/{{imageId}}
Authorization: Bearer {{adminToken}}
Content-Type: application/json
```

```json
{
  "isPrimary": true,
  "sortOrder": 1
}
```

Обидва поля обов'язкові згідно з перевірками `DataAccessor`. `sortOrder` має бути не менше нуля. Якщо `isPrimary=true`, в межах завантаженого товару головним залишається тільки вказане зображення. Якщо `false`, головний статус знімається лише з цього зображення; інші не змінюються.

Успіх — `200 OK` із `ProductImageDto` у `data`; `404 Not Found` — товар або зображення не знайдено; `400 Bad Request` — некоректні поля.

## 10. Видалити зображення

Потрібен JWT адміністратора.

```http
DELETE {{baseUrl}}/api/products/{{productId}}/images/{{imageId}}
Authorization: Bearer {{adminToken}}
```

Запис зображення видаляється з БД. Якщо видалене зображення було головним, перше з тих, що залишилися, за `SortOrder` та `Id` автоматично стає головним.

Для локального файла контролер намагається виконати фізичне видалення. Локальним вважається ключ у форматі GUID без роздільників шляху та з розширенням `.jpg`, `.png` або `.webp`. Для інших значень `ImageUrl` фізичне видалення через локальне сховище не виконується.

Звичайний успіх — `200 OK`:

```json
{
  "status": {
    "isOk": true,
    "code": 200,
    "message": "OK"
  },
  "meta": {
    "apiName": "ProductImages",
    "dataType": "json/object",
    "cacheTime": 0,
    "manipulations": ["DELETE"],
    "links": {
      "parent": "/api/products",
      "self": "/api/products/00000000-0000-0000-0000-000000000001/images/00000000-0000-0000-0000-000000000020"
    }
  },
  "data": {
    "message": "Product image deleted successfully.",
    "imageRecordDeleted": true,
    "fileCleanupCompleted": true
  }
}
```

Якщо запис у БД уже видалено, але локальний файл не вдалося прибрати через `IOException`, `UnauthorizedAccessException` або `SecurityException`, повертається `500 Internal Server Error`. У `data` будуть `imageRecordDeleted: true` і `fileCleanupCompleted: false`: запис уже видалений, але файл може залишитися у сховищі.

Якщо файл відсутній і `DeleteAsync` повертає `false`, контролер не трактує це як помилку очищення. Для нелокального ключа очищення також вважається завершеним, оскільки файл не видаляється локальним сервісом.

Якщо товар або зображення не знайдено, повертається `404 Not Found`.

## 11. Отримати файл зображення

```http
GET {{baseUrl}}/api/products/images/{{imageKey}}
```

Endpoint публічний і повертає бінарний файл із відповідним `Content-Type`. Контролер приймає ключі з розширеннями `.jpg`, `.png` та `.webp`; інші розширення повертають `400 Bad Request`.

Приклад:

```text
https://localhost:<port>/api/products/images/a1b2c3d4e5f678901234567890abcdef.webp
```

Використовуйте `imageUrl` із відповіді товару або точний `imageKey` із відповіді завантаження. Допустимий ключ має формат `32-символьний GUID без дефісів` плюс `.jpg`, `.png` або `.webp`; ключ не може містити роздільники шляхів, бути абсолютним шляхом чи вказувати за межі каталогу сховища. Ключ із непідтримуваним розширенням або некоректним форматом повертає `400 Bad Request`; якщо файл відсутній — `404 Not Found`.

## 12. Керування характеристиками

Характеристики належать конкретному товару. Публічні GET-запити доступні для активних товарів. Admin може читати характеристики неактивного товару; у адміністративних відповідях також повертається колекція перекладів.

### Структура перекладу характеристики

```json
{
  "cultureCode": "uk-UA",
  "name": "Колір",
  "value": "Чорний"
}
```

Правила `DataAccessor`:

| Поле | Правило |
|---|---|
| `cultureCode` | Лише `uk-UA` або `en-US`; повтори в межах однієї характеристики заборонені |
| `name` | Обов'язкове після обрізання пробілів; максимум 150 символів |
| `value` | Обов'язкове після обрізання пробілів; максимум 1000 символів |
| `sortOrder` | Ціле число від 0 до `2147483647` |

DTO запитів також перевіряють `sortOrder` у діапазоні `0`–`2147483647` та вимагають непорожній список `translations`. Кожен переклад має містити `cultureCode` (до 10 символів), `name` (1–150 символів) і `value` (1–1000 символів); бізнес-логіка додатково дозволяє лише `uk-UA` і `en-US` та відхиляє порожні після обрізання назви й значення.

Під час створення характеристики український переклад обов'язковий. Під час оновлення існуючої характеристики його можна не передавати: попередній переклад залишиться. Якщо переклад для обраної мови відсутній, використовується `uk-UA`.

Назви характеристик не можуть повторюватися в межах одного товару для однієї локалі без урахування регістру. Однакові назви в різних товарах або різних локалях дозволені.

### Список характеристик

```http
GET {{baseUrl}}/api/products/{{productId}}/specifications
```

Відповідь містить масив у `data`, відсортований за `sortOrder`, а потім за ID. Для Admin у кожній характеристиці додатково повертається `translations`.

### Одна характеристика

```http
GET {{baseUrl}}/api/products/{{productId}}/specifications/{{specificationId}}
```

Успіх — `200 OK` з об'єктом характеристики у `data`. Якщо товар недоступний або характеристика не належить цьому товару, повертається `404 Not Found`.

### Створити характеристику

Потрібен JWT адміністратора.

```http
POST {{baseUrl}}/api/products/{{productId}}/specifications
Authorization: Bearer {{adminToken}}
Content-Type: application/json
```

```json
{
  "sortOrder": 0,
  "translations": [
    {
      "cultureCode": "uk-UA",
      "name": "RAM",
      "value": "16 GB"
    },
    {
      "cultureCode": "en-US",
      "name": "RAM",
      "value": "16 GB"
    }
  ]
}
```

ID та ProductId визначаються сервером і в тілі не передаються. Успіх — `201 Created`; `Location` вказує на endpoint створеної характеристики. `400 Bad Request` — помилка валідації; `404 Not Found` — товар не існує; `409 Conflict` — назва перекладу вже використовується в цьому товарі для відповідної локалі.

### Оновити характеристику

Потрібен JWT адміністратора.

```http
PUT {{baseUrl}}/api/products/{{productId}}/specifications/{{specificationId}}
Authorization: Bearer {{adminToken}}
Content-Type: application/json
```

```json
{
  "sortOrder": 1,
  "translations": [
    {
      "cultureCode": "uk-UA",
      "name": "RAM",
      "value": "32 GB"
    }
  ]
}
```

Оновлення змінює `sortOrder` та додає/оновлює передані переклади. Переклади інших локалей, відсутні у запиті, не видаляються. Характеристика має належати вказаному товару.

Успіх — `200 OK`; `404 Not Found` — товар або характеристику не знайдено; `400 Bad Request` — некоректні дані; `409 Conflict` — назва вже використовується для тієї самої локалі в іншій характеристиці цього товару.

### Видалити характеристику

Потрібен JWT адміністратора.

```http
DELETE {{baseUrl}}/api/products/{{productId}}/specifications/{{specificationId}}
Authorization: Bearer {{adminToken}}
```

Успіх — `200 OK` з повідомленням `Product specification deleted successfully.` Характеристика та її переклади видаляються фізично. Якщо товар або характеристику не знайдено — `404 Not Found`.

## 13. HTTP-статуси

| Код | Значення |
|---|---|
| `200 OK` | Запит успішний; зокрема завантаження зображення також наразі повертає 200 |
| `201 Created` | Товар або характеристику створено |
| `400 Bad Request` | Некоректні параметри, поля запиту, переклади або файл |
| `401 Unauthorized` | Відсутній, недійсний або прострочений JWT для захищеної операції |
| `403 Forbidden` | JWT валідний, але користувач не має ролі `Admin` |
| `404 Not Found` | Товар, характеристику, зображення або файл не знайдено; також використовується для повторної деактивації/відновлення |
| `409 Conflict` | Конфлікт унікальності SKU, slug або назви характеристики |
| `500 Internal Server Error` | Неочікувана помилка сервера або помилка очищення файла після видалення запису зображення |

Формат тіла помилки залежить від endpoint-а: частина помилок повертається в `RestResponse`, інші — у звичайному JSON або `ProblemDetails`.

## 14. Перевірка через Postman

1. Увійдіть під адміністратором і скопіюйте `accessToken`.
2. Перевірте `GET /api/products` без токена: має повертатися публічний каталог активних товарів.
3. Створіть товар через `POST /api/products`, передавши `translations` і `specifications` у новому форматі.
4. Отримайте товар за ID та slug; перевірте локалізацію для `uk-UA` та `en-US`.
5. Завантажте зображення через `multipart/form-data`, перевірте список зображень і відкриття `imageUrl`.
6. Створіть характеристику окремим endpoint-ом, оновіть її та видаліть.
7. Оновіть товар: залиште ID існуючої характеристики, додайте нову без ID та перевірте видалення тієї, яку не передали.
8. Деактивуйте товар і перевірте, що публічний каталог та публічні GET-запити його більше не повертають.
9. Відновіть товар і повторіть публічний запит.
10. Повторіть адміністративний endpoint із токеном `User`: очікується `403 Forbidden`.
